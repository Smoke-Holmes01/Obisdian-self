### 项目一：企业级多源融合金融研报分析系统（Advanced RAG + 结构化生成）
- **业务背景**：传统研报动辄上百页，包含大量多栏排版、跨页嵌套财务报表及行业对比图表，传统纯向量 RAG 存在严重的数字丢失、跨页断句与幻觉问题。
- **核心架构**：
  ```mermaid
  flowchart LR
      Doc[研报 PDF] --> Parser[MinerU 深度版面解析]
      Parser --> ContextualChunk[Contextual Retrieval 上下文增强分块]
      ContextualChunk --> VectorDB[(Qdrant 向量库 + BM25 倒排)]
      
      Query[分析师提问] --> QueryRewrite[意图改写与子查询拆解]
      QueryRewrite --> Hybrid[混合检索 (Dense+Sparse)]
      Hybrid --> RRF[RRF 倒数排名融合]
      RRF --> Reranker[BGE-Reranker-large 深度重排]
      Reranker --> LLM[大模型事实 Grounding 综合推导]
      LLM --> Artifact[结构化 Markdown / Docx 导出]
  ```
- **核心攻关亮点**：
  1. **复杂表格精准还原**：采用版面分析工具提取表格为 Markdown Table，结合上下文增强分块（Contextual Retrieval），为每个分块自动注入文档级背景说明。
  2. **混合检索与深度重排**：构建“BGE-M3 稠密向量 + BM25 稀疏检索”双路召回，经 RRF 排名融合后输入 Cross-Encoder 重排模型，Top-5 召回准确率提升 31%。
  3. **量化评测体系**：基于 Ragas 框架构建包含 300 组 Golden QA 的自动化评测集，使 Faithfulness（事实忠实度）达到 0.94，Answer Relevance 达到 0.91。

### 项目二：基于 LangGraph 的全自动数据分析与代码沙箱 Agent
- **业务背景**：业务人员上传 CSV/Excel 文件后，系统通过自然语言交互自动拆解指标计算需求，自主编写 Python 脚本、在安全沙箱中执行、绘图并导出分析看板。
- **核心架构**：
  - **状态机设计**：采用 **LangGraph** 构建有向循环图，包含 `Planner`（全局规划）、`Coder`（代码生成）、`Executor`（沙箱执行器）、`Reflector`（自检反思纠偏）四大节点。
  - **环境隔离与安全性**：基于 **Docker 容器沙箱** + 资源配额（cgroups 限制 CPU 2核/内存 1G，彻底禁用外网访问），杜绝恶意代码危害宿主机。
  - **协议标准化**：将沙箱代码执行与图表导出封装为标准 **MCP Server（Model Context Protocol）**，支持跨端复用。
- **技术突破与量化成果**：
  - 设计 **Reflexion 自动化纠偏机制**：当沙箱抛出 `SyntaxError` 或 `KeyError` 时，拦截 Traceback 回灌模型，结合最近历史实现自我修复，复杂长链路任务单次运行成功率由 **58% 提升至 89%**。

### 项目三：多智能体协同企业工单流转与客户服务系统（MAS + 人机在环）
- **业务背景**：处理企业多部门跨系统复杂业务办理，解决单一 Agent 职责膨胀导致指令漂移、无法应对高危资金/数据变更操作的弊端。
- **核心架构**：
  - **协同拓扑**：采用 **Supervisor（主管中枢）分级协作模式**，下设“接待分流 Agent”、“技术排障 Agent”、“财务退款 Agent”。
  - **人机在环（Human-in-the-Loop）**：关键高危操作（如单笔大于 ¥1,000 的退款或权限变更）自动触发 `interrupt()` 挂起，生成管理员审批待办；审批通过后依据 `thread_id` 恢复上下文继续流转。
  - **全生命周期可观测**：全量接入 **Langfuse**，针对每一步 Agent 决策做 Trace/Span 级耗时分解与 Token 消耗审计。
- **量化成果**：
  - 引入 **Prompt Caching**，对静态规则和系统提示做前缀缓存，综合 Token 成本降低 **54%**，系统端到端高危操作误触率为 **0%**。

## 二、 经典高频面试深度八股与应答策略

### Q1：Function Calling 和 ReAct 模式的本质区别与联系是什么？
- **标准回答**：
  - **联系**：ReAct 是一种**认知推理范式（Thought -> Action -> Observation）**，而 Function Calling 是底层模型厂商（如 OpenAI、Anthropic）在 API 层面提供的**原生结构化工具输出协议支持**。
  - **区别**：早期 ReAct 依赖纯 Prompt 引导模型在文本中输出特定前缀（如 `Action: query_weather[太原]`），由外部代码用正则表达式解析，极易格式错乱；现代智能体通常**以 ReAct 作为控制流逻辑核心，同时底层调用原生的 Function Calling / Structured Outputs 来实现高可靠的参数结构化提取与函数分发**。

### Q2：如果两个 Agent 在多智能体系统中陷入“互相质询、踢皮球”的死循环，你在架构上怎么防御？
- **标准回答**：
  - **硬性全局限制**：在状态图引擎层设置 `max_iterations` 或 `max_turns`（例如 10 轮），达到上限强制收敛并抛出异常。
  - **中心化仲裁机制（Supervisor）**：禁止 Agent 间无序点对点广播，所有流转必须经过 Supervisor 节点汇总研判；
  - **状态去重与震荡检测**：对每次流转的状态摘要做哈希校验，若检测到最近 3 次交互的状态相似度超过阈值，判定为逻辑震荡，立即触发降级转人工（Human-in-the-Loop）。

### Q3：如何解决 RAG 中的“检索到了正确资料，但大模型依然回答错误（幻觉）”的问题？
- **标准回答**：
  - ① **检查 Lost in the Middle 效应**：查看命中分块是否被夹在超长上下文中间，应将最相关的核心证据重排（Rerank）后放置在最靠近用户提问的位置；
  - ② **加固 Grounding 约束 Prompt**：在 System Prompt 明确强制要求：“请逐句根据 `<context>` 内部的事实回答，每个关键结论必须引用源文本中的具体句子；严禁推测未知内容”；
  - ③ **降低采样随机性**：将 Temperature 调至 0.0，Top-p 设为 0.1；
  - ④ **引入验证器（Verifier）做二次评估**：在输出给用户前，利用轻量模型对生成的答案做 Faithfulness 快速校验，若未通过则重写。

### Q4：在面试中被问到“请谈谈你遇到过的最棘手的一个 Bad Case 以及你是如何排查解决的？”
- **回答模板（建议提前熟记）**：
  - **背景**：在智能报表生成项目中，模型在解析“同比”和“环比”指标时，经常调用错 SQL 工具参数，导致生成的财报数据完全颠倒。
  - **排查**：调取 **Langfuse 链路追踪**，定位到该步骤的 Generation 详情，发现两个根因：一是工具 Description 中对两个参数的区分描述过于简略；二是用户提问常常带有自然语言模糊性（如“比上个月”被误判为“去年同期”）。
  - **解决**：① 在 Tool Schema 的参数 `description` 中增加了 2 个典型的 Few-shot 区分示例，并明确了反向排除规则；② 在调用该工具前增加了一道独立的“指标消歧节点”；③ 将该场景抽象为 20 个测试 Case 纳入自动化回归评测流水线。
  - **结果**：该类型指标计算的准确率从 72% 提升至 98% 以上。
